1. EXECUTIVE SUMMARY & SYSTEM OVERVIEW
--------------------------------------------------------------------------------
Jadavpur Love Birds is a mobile-first campus dating application architected 
specifically for university students. It combines verified student onboarding 
with complete chat privacy and female-first security controls.

Core Architectural Pillars:
1. Zero-Cloud Chat Storage:
   Chat messages and shared media files NEVER touch any backend database, cloud 
   storage bucket, or third-party server. All messages exist exclusively within 
   the client-side IndexedDB database (via Dexie.js) on the participants' 
   devices.
2. Direct WebRTC P2P DataChannel:
   Text messages and media attachments are transmitted directly between peers 
   over encrypted WebRTC DataChannels using ephemeral signaling (via Supabase 
   Realtime broadcast) and Google STUN servers.
3. Delivery Status Lifecycle (WhatsApp-Style Ticks):
   Full acknowledgment protocol implementing Single Gray Tick (sent), Double 
   Gray Tick (delivered), and Double Green Tick (read), updated reactively 
   through bidirectionally exchanged ACK packets.
4. Female-First Safety & Media Gating:
   - Initiation: Male users are blocked from sending signaling offers until the 
     female user makes the first move.
   - Media Guard: Female users possess master toggle authority over media sharing. 
     If a male user transmits media while media is disabled, the female client 
     instantly drops the packet, and the male client UI locks media attachments.
5. Campus Verification & Zero-Knowledge Hashing:
   Students verify identity by scanning physical university library card barcodes 
   via device camera or image upload. Raw card numbers are NEVER transmitted; 
   they are hashed client-side with SHA-256 before registration.
6. Public Safety Transparency:
   Every profile displays live, community-visible counters ("Reported: X times", 
   "Blocked: Y times") driven by atomic PostgreSQL database triggers to expose 
   bad actors transparently.
7. Biometric & Instant Background Lock:
   The app continuously monitors OS focus state (`visibilitychange` and `blur`) 
   and immediately locks behind a 4-digit SHA-256 PIN or WebAuthn biometrics 
   (FaceID/Fingerprint) with haptic failure feedback.
8. Universal Zero-Cost Deployment:
   - iOS: Installable Progressive Web App with standalone full-screen display, 
     custom icon masking, and iOS Safari Add-to-Home-Screen prompt banner.
   - Android: Capacitor native bridge compiling directly to `JadavpurLoveBirds.apk` 
     via local bash script (`build-apk.sh`) or free cloud CI/CD via GitHub Actions.

4. DATABASE & CLOUD DATA LAYER (SUPABASE POSTGRESQL + REALTIME)
================================================================================
File: supabase/migrations/001_initial_schema.sql

4.1 PostgreSQL Schema Architecture
----------------------------------
The database stores ONLY user profiles, match relationships, blocks, and reports.
NO CHAT MESSAGES OR CHAT MEDIA ARE EVER STORED ON THE SERVER.

Tables:
1. `public.profiles`:
   - `id` (uuid, primary key, references auth.users on delete cascade)
   - `full_name` (text, not null)
   - `gender` (text, check in ('male', 'female', 'other'), not null)
   - `target_gender` (text, check in ('male', 'female', 'all'), default 'all')
   - `age` (int, check >= 18, not null)
   - `bio` (text, default '')
   - `insta_handle` (text, unique, not null)
   - `library_card_hash` (text, unique, not null) -- SHA-256 client hash
   - `photo_urls` (text[], default empty array)
   - `is_verified` (boolean, default false)
   - `report_count` (int, default 0, not null) -- Community safety counter
   - `block_count` (int, default 0, not null)  -- Community safety counter
   - `created_at` (timestamptz, default now())
   - `updated_at` (timestamptz, default now())

2. `public.matches`:
   - `id` (uuid, primary key, default uuid_generate_v4())
   - `female_id` (uuid, references public.profiles(id) on delete cascade)
   - `male_id` (uuid, references public.profiles(id) on delete cascade)
   - `has_female_initiated` (boolean, default false, not null)
   - `media_allowed` (boolean, default false, not null)
   - `matched_at` (timestamptz, default now())
   - UNIQUE constraint on `(female_id, male_id)`

3. `public.blocks`:
   - `id` (uuid, primary key, default uuid_generate_v4())
   - `blocker_id` (uuid, references public.profiles(id) on delete cascade)
   - `blocked_id` (uuid, references public.profiles(id) on delete cascade)
   - `created_at` (timestamptz, default now())
   - UNIQUE constraint on `(blocker_id, blocked_id)`

4. `public.reports`:
   - `id` (uuid, primary key, default uuid_generate_v4())
   - `reporter_id` (uuid, references public.profiles(id) on delete cascade)
   - `reported_id` (uuid, references public.profiles(id) on delete cascade)
   - `reason` (text, not null)
   - `created_at` (timestamptz, default now())

4.2 Atomic Database Functions & Triggers
----------------------------------------
To prevent race conditions and guarantee transparent community safety metrics:

- `handle_new_block()`:
  Trigger function executing `AFTER INSERT ON public.blocks`.
  Atomically updates `public.profiles SET block_count = block_count + 1 WHERE id = NEW.blocked_id`.
  Runs with `SECURITY DEFINER` privileges.

- `handle_new_report()`:
  Trigger function executing `AFTER INSERT ON public.reports`.
  Atomically updates `public.profiles SET report_count = report_count + 1 WHERE id = NEW.reported_id`.
  Runs with `SECURITY DEFINER` privileges.

4.3 Row-Level Security (RLS) Policy Specifications
--------------------------------------------------
- "Profiles viewable except if blocked":
  Authenticated users can select profiles EXCEPT any user they have blocked, OR 
  any user who has blocked them. Mutual invisibility is strictly enforced at 
  the SQL engine level.
- "Users can update own profile":
  `auth.uid() = id`.
- "View matches":
  Users can only query rows where `auth.uid() = female_id OR auth.uid() = male_id`.
- "Female controls initiation & media permissions":
  `UPDATE ON public.matches` is restricted to `auth.uid() = female_id`. Male users 
  cannot alter `has_female_initiated` or `media_allowed` via API.
- "Insert blocks" & "Insert reports":
  Strict validation that `auth.uid() = blocker_id` / `reporter_id`.

4.4 Ephemeral Realtime Broadcast for Signaling
----------------------------------------------
Channel: `signal:${matchId}`
Payloads exchanged:
- `{ type: 'offer', senderId, sdp }`
- `{ type: 'answer', senderId, sdp }`
- `{ type: 'candidate', senderId, candidate }`
These signals are ephemeral broadcasts with `broadcast: { self: false }`. They 
are NEVER committed to PostgreSQL table storage.

Indexes: `id, matchId, senderId, status, timestamp, [matchId+timestamp]`

- `matchId`: Correlation ID linking message to match
- `senderId`: Profile ID of sender
- `text`: Optional text body
- `mediaBlob`: Optional base64 or blob URL of image attachment
- `mediaType`: MIME type (e.g., 'image/jpeg', 'image/png')
- `status`: MessageStatus enum ('sending' | 'sent' | 'delivered' | 'read')
- `timestamp`: Epoch milliseconds

5.2 Zero Cloud Message Storage Guarantee
----------------------------------------
Under no circumstances are `local_messages` transmitted to Supabase or any REST/GraphQL 
endpoint. If a user deletes their local data or uninstalls the app, local chat history 
is destroyed. When a user blocks another peer, `db.deleteMessagesForMatch(matchId)` 
is invoked immediately, wiping local chat records.

6. P2P WEBRTC DATACHANNEL ENGINE & PROTOCOL SPECIFICATION
================================================================================
File: src/services/p2pChat.ts

6.1 Message Packet Protocol
---------------------------
All communication over the WebRTC `RTCDataChannel` (named `p2p-chat`, ordered: true) 
conforms to the following discriminated union:

```typescript
export type P2PPacket = 
  | { 
      type: 'chat'; 
      id: string; 
      senderId: string; 
      text?: string; 
      media?: { blob: string; mimeType: string }; 
      timestamp: number;
    }
  | { 
      type: 'ack'; 
      messageId: string; 
      status: 'delivered' | 'read';
    };
```

6.2 The WhatsApp Delivery Tick Protocol Lifecycle
-------------------------------------------------
State                  Visual Tick       Trigger Condition
--------------------------------------------------------------------------------
1. 'sending'           Clock icon        Local message object created, awaiting dataChannel write.
2. 'sent'              Single Gray Check Packet successfully pushed to RTCDataChannel (`channel.send()`).
3. 'delivered'         Double Gray Check Remote peer received packet via `channel.onmessage` and 
                                         immediately dispatched `{ type: 'ack', messageId, status: 'delivered' }`.
4. 'read'              Double Green Check Recipient chat viewport is open/active (`isChatWindowActive === true`), 
                                         dispatching `{ type: 'ack', messageId, status: 'read' }`.

Handling Incoming ACKs:
When an ACK packet arrives over the DataChannel, `P2PChatEngine` executes:
1. `await db.updateMessageStatus(packet.messageId, packet.status)` in Dexie.js.
2. Invokes reactive callback `onAckReceived(messageId, status)` to update React state.

6.3 Female-First Initiation Rule Enforcement
--------------------------------------------
Signaling Logic:
- Male Client:
  Upon mounting `P2PChatEngine`, if `currentProfile.gender === 'male'` and 
  `matchInfo.has_female_initiated === false`, the engine sets state to 
  `waiting_for_female_initiation` and HALTS all signaling. It does not create 
  or dispatch an SDP offer.
- Female Client:
  Upon opening the chat, the female client:
  1. Invokes `api.setFemaleInitiated(matchId)` which updates `has_female_initiated = true` in Supabase.
  2. Creates the RTCDataChannel (`createDataChannel('p2p-chat')`).
  3. Creates the initial SDP Offer (`createOffer()`) and dispatches it over the ephemeral 
     Supabase broadcast channel.
  4. The male client receives the offer, creates an SDP Answer, and establishes the peer connection.

6.4 Media Protection Guard
--------------------------
1. UI Level:
   If `currentProfile.gender === 'male'` and `matchInfo.media_allowed === false`, 
   the media attachment input button in `ChatRoom.tsx` is disabled and locked with 
   a tooltip: "Only she can enable media sharing".
2. Transmission Level:
   `sendMessage(text, media)` validates:
   `if (media && !isFemale && !matchInfo.media_allowed) throw new Error("Only she can enable media sharing");`
3. Receiving Defense-in-Depth Level:
   When a packet arrives at `handleIncomingPacket`:
   `if (packet.media && this.isFemale && !this.matchInfo.media_allowed) return; // DROP PACKET IMMEDIATELY`
   Unauthorized media packets are dropped before hitting storage or DOM.

7. CRYPTOGRAPHY, IDENTITY VERIFICATION & SECURITY LOCK
================================================================================
Files: src/utils/crypto.ts, src/pages/Auth.tsx, src/components/LockScreen.tsx

7.1 Student Identity Verification (ZXing Library)
-------------------------------------------------
Step 1 of Onboarding:
- Scans physical University Library Card barcode via device camera using 
  `BrowserMultiFormatReader` from `@zxing/library`, or via file upload.
- Supports Code 128, Code 39, EAN-13, and QR codes.
- Zero-Knowledge Privacy Hashing:
  ```typescript
  export async function sha256(message: string): Promise<string> {
    const msgUint8 = new TextEncoder().encode(message);
    const hashBuffer = await crypto.subtle.digest('SHA-256', msgUint8);
    const hashArray = Array.from(new Uint8Array(hashBuffer));
    return hashArray.map((b) => b.toString(16).padStart(2, '0')).join('');
  }
  ```
  The raw barcode string is immediately hashed. Only the 64-character SHA-256 
  hex digest is stored in `public.profiles.library_card_hash`. Raw student card 
  numbers never touch the database.

7.2 Instagram Verification
--------------------------
- Enforces strict regex validation: `/^@[a-zA-Z0-9._]{1,30}$/`.
- Displayed prominently on all profile cards with deep links to Instagram profiles.

7.3 4-Digit Master PIN & WebAuthn Biometrics
--------------------------------------------
- Setup: User chooses a 4-digit PIN. Hashed with client-side SHA-256 and stored in 
  `localStorage.getItem('jud_user_pin_hash')`.
- WebAuthn Integration:
  Uses `navigator.credentials.create` and `navigator.credentials.get` with 
  `userVerification: 'required'` to register and authenticate using FaceID, 
  TouchID, or Android Biometric Prompt.
- Haptic Failure Feedback:
  On incorrect PIN entry or rejected biometric challenge:
  `navigator.vibrate([100, 50, 100])` triggers device vibration feedback.

7.4 Instant Backgrounding Auto-Lock
-----------------------------------
File: src/components/SecurityLock.tsx
Listens continuously to browser lifecycle events:
```typescript
document.addEventListener('visibilitychange', () => {
  if (document.hidden) setIsLocked(true);
});
window.addEventListener('blur', () => {
  setIsLocked(true);
});
```
When the user switches tabs, minimizes the browser, or switches native apps on 
Android/iOS, the app instantly activates the full-screen `LockScreen` modal.

9.3 Local Compilation Pipeline (`build-apk.sh`)
-----------------------------------------------
An executable script performing end-to-end automated compilation:
1. Rebuilds web bundle: `npm run build`.
2. Syncs web assets to Android project: `npx cap sync android`.
3. Grants execution rights: `chmod +x android/gradlew`.
